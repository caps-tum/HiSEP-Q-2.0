# QSG Measure Functional Specification

This note records the current `QSG-MEASURE` behavior in the project. It is
meant to describe the implemented control flow, the top-level interface, and
the expected simulation behavior.

## Scope

The change applies only to `QV.SINGLE` (`QSG`).

- `funct7[31:25]` continues to carry `GateID`
- `GateID = 7'h68` is reserved for `MEASURE`
- all other `GateID` values keep the current non-measure `QSG` behavior

The existing `QSG` operand/export semantics remain in place:

- `elem1` carries the qubit index stream from `vs1`
- `elem2` carries the 32-bit scalar payload selected by instruction bits `[24:20]`
- `elem3` carries the packed control metadata for `QSG`

This document only defines the additional control flow and external handshake
required for the `MEASURE` gate.

## New Top-Level Signals

`qvproc_top` exposes the following signals.

Outputs:

- `qvsg_meas`
  - a measure interrupt request generated by `QSG-MEASURE`
  - in the current RTL this signal is active-high
  - it is wired into the Ibex interrupt path through `qvproc_top`

- `measure_issued_done`
  - indicates that the current `QSG-MEASURE` instruction has finished issuing
    all of its `elem1` entries to the quantum backend
  - value is normally `0`
  - when asserted, it must remain `1` for exactly `2` clock cycles

Input:

- `measure_done`
  - external completion input from the quantum backend ADC
  - default value is `0`
  - when asserted, it indicates that the backend has completed the full
    measurement sequence and the machine may resume

## Functional Intent

When `QSG` is decoded with `GateID = 7'h68`, the instruction is treated as a
measurement request.

The intended flow is:

1. `QSG-MEASURE` is decoded.
2. `qvsg_meas` is asserted immediately.
3. New Ibex-to-vproc offload work is blocked immediately after the measure
   becomes active.
4. Ibex enters interrupt mode as quickly as its native interrupt mechanism
   allows.
5. vproc does **not** stop immediately. It continues executing the current
   `QSG-MEASURE` instruction until the full `elem1` stream has been issued.
6. Once the current `QSG-MEASURE` has issued all of its `elem1` values,
   `measure_issued_done` is asserted for 2 cycles.
7. After the active measure stream drains, the queue-to-dispatch path is held
   so younger vector work cannot cross the pause boundary.
8. The machine remains paused until external `measure_done` is asserted.
9. When `measure_done` is asserted:
   - `qvsg_meas` is deasserted
   - the pause is released
   - Ibex and qvproc resume normal execution

## Timing Rules

The timing rule that matters most is:

- Ibex stops early.
- vproc stops late.

More precisely:

- `qvsg_meas` becoming active causes Ibex to begin its normal interrupt entry
  flow immediately.
- vproc must be allowed to drain the currently active `QSG-MEASURE` instruction.
- Only after the current measure instruction has fully issued its `elem1`
  sequence may vproc enter the paused state.

This is intentionally asymmetric. Ibex is interrupt-driven, while vproc still
has work to finish for the currently active measure instruction.

## Definition of "Measure Instruction Complete"

For this feature, the current `QSG-MEASURE` instruction is considered complete
for issuing purposes only when:

- all `elem1` entries belonging to that instruction have been exported toward
  the quantum backend

It is **not** enough that the instruction was decoded or that its first event
appeared in the quantum trace.

The completion pulse is:

- `measure_issued_done = 1`
- for `2` clock cycles

## Ibex-Side Handling

Ibex must use its existing interrupt/trap machinery as much as possible.

Current implementation goal:

- prefer the smallest change that uses Ibex's native interrupt response
- avoid inventing a parallel interrupt handling path outside Ibex's normal
  control flow

Behavioral requirement:

- once `qvsg_meas` is asserted, Ibex should stop fetching and advancing normal
  work as soon as its interrupt model permits

Important constraint:

- in-flight Ibex instructions must be handled consistently with the existing
  Ibex interrupt semantics
- no half-committed architectural state should be created by the measure
  interrupt path

## vproc-Side Handling

vproc must distinguish between:

1. the currently active `QSG-MEASURE`
2. any later instructions already present in the machine

Required behavior:

- the current `QSG-MEASURE` is allowed to continue until all of its `elem1`
  values have been issued
- later work must not continue beyond the pause boundary

Current control strategy:

- stop accepting new offload work as soon as the measure becomes active
- allow only the active measure instruction to drain
- once the active measure instruction drains, stall later vproc work at the
  queue-to-dispatch boundary

This is preferred over a broad flush unless an existing control path forces a
flush to preserve correctness.

## In-Flight Pipeline Instructions

The implementation must explicitly consider instructions already present in the
pipelines when `qvsg_meas` is asserted.

### Ibex

At interrupt assertion time, some scalar instructions may already be in IF, ID,
EX, or WB stages.

Required policy:

- respect Ibex's native interrupt boundary rules
- reuse existing flush/stall behavior where possible
- do not create a new qvproc-specific exception model for Ibex

### vproc

At measure assertion time, vector work may already exist in dispatcher,
pipeline, unpack, unit, result, or writeback paths.

Required policy:

- the current `QSG-MEASURE` may continue
- instructions younger than the active measure must not keep generating visible
  side effects once the pause boundary is reached
- the design must prevent later vector instructions from silently running past
  the measure barrier

Preferred minimum-change approach:

- stall first
- flush only where strictly necessary

## Pause / Resume Contract

Paused state:

- Ibex is already in interrupt mode
- vproc has finished issuing the active `QSG-MEASURE`
- `measure_issued_done` has already been emitted
- the system waits for `measure_done`

Resume condition:

- `measure_done == 1`

On resume:

- clear `qvsg_meas`
- release the vproc pause
- allow Ibex and qvproc to continue with subsequent program execution

## Testbench Requirements

The testbench should model the complete halt-resume sequence.

The current QSG testbench does the following:

1. execute a `QSG-MEASURE` instruction
2. print the following signals during simulation:
   - `qvsg_meas`
   - `measure_issued_done`
   - `measure_done`
3. show that Ibex enters interrupt handling quickly after `qvsg_meas`
4. show that vproc continues until the current `QSG-MEASURE` has fully issued
5. hold `measure_done=0` for `50` simulated clock cycles after
   `measure_issued_done`
6. assert `measure_done=1`
7. confirm that execution resumes afterward

## Current Scope Boundaries

The current implementation is intentionally narrow.

It does not attempt to solve:

- multiple outstanding measurement commands
- a general backend transaction queue
- speculative overlap of post-measure scalar work
- interrupt prioritization beyond the existing Ibex behavior

## Summary

`QSG` with `GateID = 7'h68` is a special measurement instruction that:

- asserts `qvsg_meas`
- causes Ibex to enter interrupt mode quickly
- allows the current measure instruction in vproc to finish issuing all
  `elem1` entries
- pulses `measure_issued_done` for 2 cycles
- pauses the machine while waiting for external `measure_done`
- resumes normal execution once `measure_done` arrives

The critical correctness rule is that the active `QSG-MEASURE` must drain, but
younger in-flight work must not cross the pause boundary incorrectly.
